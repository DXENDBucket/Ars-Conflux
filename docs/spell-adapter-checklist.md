# 原生法术接入核对

适用于 Iron、Goety 和以后的法术提供者。新增魔符时，先在提供者仓库写出该法术的行为清单，再决定是否能复用已有适配器。这里规定核对方法，不要求不同模组共用召唤、等级或装备机制。

## 先确认实际接入范围

核对固定依赖 JAR 对应的源码与行为。上游最新分支可能与实际发行包不同；两个 Minecraft 版本也不能只凭类名相同就判断一致。

先填写这些内容：

| 项目 | 要记录的内容 |
| --- | --- |
| 原生入口 | 聚晶／法术 ID、实体类型、`start`、`use`、`result`、`stop` 是否都参与执行。 |
| 触发语义 | 替换弹射物、命中后效果、自身增益、持续施法或召唤；哪一个入口才算真正成功。 |
| 参数单位 | 默认值、增强映射、上下限；时长是 tick、秒、分钟还是额外倍率。 |
| 分支 | 法杖、盔甲、饰品、附魔、潜行、环境、目标种类和平台差异。 |
| 已保留／未实现 | 每个行为分别写明；不能用“已创建原生实体”替代完整核对。 |

不能盲调一次 `SpellResult`：它可能重新读取视线、忽略 Ars 命中点，也可能只占原生流程的一部分。例如有些区域在 `startSpell` 中生成，持续法术还依赖同步状态、结束回调或逐 tick 消耗。

## 目标、来源和资源各自保留身份

- 使用 Core 的 `CastContext` 区分原施法者、实际执行者、伤害所有者、付款账户、命中目标／位置和入射方向。
- 目标喷吐或接受增益，不代表目标成为伤害来源、装备提供者或付款者。
- 自身、实体命中、方块命中分别检查。让施法者背对选中的目标，能发现适配器重新读取视线的问题。
- 友军检查以原施法者为基准；保留原生主人、仆从、队伍、友伤配置和目标豁免。
- 解析器克隆、延迟、嵌套、载体转换及命中接续必须保留源上下文。提供者这次原生计费不能覆盖后续其他提供者的源账户。

## 弹射物不能只保留命中伤害

逐项核对出生位置、初始朝向、发射／转向动画、初速、加速度、阻力、重力、水中行为、追踪，以及飞行声音和尾迹。

普通飞行尽量让原生实体 tick；环绕、回响等特殊 Ars 载体由 Core 保留其轨迹。受联动管理与由 Ars 接管移动是不同状态，不能因为标记为管理实体就取消全部原生更新。原生伤害、渲染、客户端子类 tick 和命中特效仍应执行。

命中核对至少包括：

- 实体和方块都能触发完整原生处理，保留粒子、声音、击退、状态、爆炸及命中后生成的区域或子实体。
- 原生碰撞事件、目标过滤、穿透、敏感、弹跳和载体代理排除规则仍有效。
- 原生命中后，剩余 Ars 编排只执行一次。持续载体需要延后丢弃时，仅延后必要的移除，不跳过命中处理。
- 出生、命中、自然到期、资源不足、主人消失、世界卸载和服务器停止后的实体／会话清理都明确。长寿命原生召唤物不能直接套短时弹射物会话。
- 无速度增强时，对照真实原生法术逐 tick 比较运动和转向。加速使用 Ars 的增强统计，不能把发射误差当成速度倍率。

## 资源、持续行为和失败

费用来自各法术自己的定义。报价必须只读，不能触发扣费事件、生成实体或改变冷却。真正激活时才按最终价格检查并提交；生成失败或无效目标按提供者明确的成功规则处理。

同一个物理资源池使用同一个预留键。普通发射通常付一次；持续载体每次激活、持续法术的维护和召唤物后续维护是不同语义，要分别记录。创造模式、替代资源配置、非玩家和原生装置施法均要有明确行为，不能因不支持某种账户而免费施法。

散射不足应让 Ars 以可负担数量重新生成完整散射，而不是截取已生成的半边。检查重复触发余额归零后停止，以及原生命中接其他提供者时不会把费用错误导入本提供者资源池。

原生吟唱、冷却、移动限制或维护费用没有接入时要明确写出来，不把“施法效果可用”描述成“原生整套机制已兼容”。

## 客户端和服务端是独立边界

**先确认世界是服务端，再查询服务器施法者或启动执行。** 不能先调用 Ars 的 `getUnwrappedCaster()`，再检查返回实体的世界：缺少实体施法者时，它可能把 `ClientLevel` 强转为 `ServerLevel` 创建假玩家。这是此前用户崩溃报告中的真实路径，见 [端侧异常记录](side-boundaries.md)。公共读取使用 `ArsSpellAccess.caster` 或安全的 `CastContext` 入口。

- 实体生成包在客户端加入实体时，不再次转换载体、扣费、生成子实体或建立服务端会话。
- 客户端仅处理同步后的运动、模型、粒子、声音和界面；服务端负责判断、伤害、资源和权威生命周期。
- 需要在客户端读取的管理标记、运动模式和速度必须同步。普通字段不能假设会跨网络传输。
- 粒子或原生渲染器存在，不代表网络状态正确。不能只凭服务端看到实体就认为客户端外观完整。
- 公共初始化和服务端类不直接链接客户端专用类；专用服务器要能无窗口启动。
- 网络处理确认主线程、当前世界／维度、实体身份及可空字段；缺少 UUID、世界或未绑定解析器时安全退出。
- 不用客户端运行时错误来证明服务端逻辑正确；服务端 GameTest 也不能证明真实客户端生成包和视觉路径正常。

## 双版本和可选联动

共享目标语义和参数逻辑；注册、效果 Holder、附魔键、实体构造签名等差异留在平台适配中。分别构建 1.21.1 NeoForge 与 1.20.1 Forge 的可发布包，避免把开发用薄包当作 Forge 发行包。

可选载体和 Hex Linker 由 Core 接入，提供者不复制两份兼容。不链接未安装附属的类，不把另一法术提供者变成硬前置。开发目录启动和发行 JAR 的 Mixin 注册方式可能不同：确认测试启动实际加载 Core 配置。

魔符保持真实形态／效果／增强类别；通过 `GlyphPresentation` 登记展示分组。图标引用的原生模型在两个依赖 JAR 中都应存在，模型引用不等于已重新分发素材。

## 集中验证并记录证据

新增行为集中做必要验证，已有检查通过后，只有新改动或失败才重复。记录依赖版本、日志、实际通过项目和未覆盖范围：

1. 两版本编译与发行包检查。
2. 有针对性的原生世界行为：实际命中、状态／区域、运动或寿命；不只断言实体生成。
3. 必要的资源失败、重复触发和跨提供者接续。
4. 专用服务器启动与无可选附属加载。
5. 实机观察：单人与多人、出生和飞行方向、命中方块／实体、粒子、声音、清理、图标和页面类别。

最后一项未执行时明确保留“待实机确认”。服务端模型属性或转向数值正确，不等于实际动画、透明度和粒子已经目视验证。

引用或改写上游实现时核对具体文件许可证，保留必要署名和许可；特别注意同一仓库可能对原作者部分与移植者新增部分采用不同条款。

## 多次输入与暂停编排

- 输入端点和暂停游标使用 Core 公共 API；选点、操控、重施数量、费用与原生冷却由法术提供者定义。
- 在当前游标捕获 continuation，再停止原始解析器；完成时从游标续接，不能重新 `onResolveEffect` 重放前缀。
- 自定义主动入口应在吟唱／Mana／CD 预检前路由已存在的输入会话；首次启动和后续操作分开核对。
- 明确拒绝输入是否消耗操作、哪些成功操作续期、超时是完成还是取消，以及换工具／术式／维度／主人消失的行为。
- 恢复预设工具授权与执行上下文；只有真正成功的原生生成才能续接后面的编排。
- 原生实体还可能自行拒绝退化几何，例如过短火墙；测试正常有效路径与取消路径，避免把原生几何检查误当成会话丢失。
- 服务端测试不能代替客户端输入、提示、粒子、模型和连续操作的人工检查。
